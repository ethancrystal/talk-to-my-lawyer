# SEO Audit — talk-to-my-lawyer.com

**Date:** 2026-06-28
**Scope:** All public/marketing pages of the live site + the repo's SEO implementation
**Method:** Live HTTP inspection of production (raw HTML, headers, robots.txt, sitemap.xml across all host variants) cross-referenced against the source in this repo.

> **Note on quantitative data:** Semrush MCP access is not included in the current Semrush plan, so live rankings/traffic/backlink numbers could not be pulled. This audit therefore focuses on **crawlability and indexability** — the factors that set the *ceiling* on organic visibility — plus on-page best practices. To get ranking/traffic numbers, connect Google Search Console (see P0-4) or upgrade Semrush.

---

## TL;DR — Visibility Verdict

The repository's SEO implementation is **genuinely good** — comprehensive per-page meta tags, canonicals, Open Graph/Twitter cards, JSON-LD structured data (Organization, LegalService, FAQPage, BreadcrumbList, Article, ItemList), a thoughtful robots.txt with a search-yes/train-no AI policy, an `llms.txt`, a complete sitemap, and Bing verification.

**But the site is leaving most of that value on the table in production, for three reasons:**

| # | Severity | Issue | Effect on visibility |
|---|----------|-------|----------------------|
| **P0-1** | 🔴 Critical | **Production is serving a stale build.** The deployed `index.html` is missing the JSON-LD, the Bing verification meta, the improved OG title, and still contains a zoom-blocking viewport — all of which are already fixed in this repo but not live. | Search engines see an older, weaker page than the code you've written. A deploy is a free, large win. |
| **P0-2** | 🔴 Critical | **Duplicate domains with no canonicalization.** `talk-to-my-lawyer.com`, `www.talk-to-my-lawyer.com`, and `www.talkmylawyer.com` all return `200 OK` with byte-identical content (same ETag) — none redirect to a canonical host. The live robots/sitemap point to `www.talkmylawyer.com` while `og:url` points to `www.talk-to-my-lawyer.com`. | Link equity and crawl budget are split across 3+ identical sites; Google must guess the canonical and may index the wrong domain. |
| **P0-3** | 🟠 High | **100% client-side rendering, empty HTML shell.** Every route ships `<body><div id="root"></div></body>` with no pre-rendered content, and every route serves the *same* static `<title>`/description until JavaScript runs. Real titles, content, canonicals, and structured data are injected by `react-helmet-async` after hydration. | Googlebot can render JS (so it mostly works), but Bing, social scrapers, and AI answer engines that don't execute JS see a near-empty, undifferentiated page on every URL. Caps the indexable surface and rich-result eligibility. |

Fixing P0-1 and P0-2 requires **no application code changes** — they are a deploy and an infra/DNS change. They are the highest-leverage actions available.

## 1. What's Already Done Well (keep it)

These are implemented correctly in the repo and should be preserved:

- **Per-page meta**: Every public page (`Home`, `Pricing`, `FAQ`, `Terms`, `Privacy`, `BlogIndex`, `BlogPost`, `ServicesIndex`, `ServicePage`) sets a unique `<title>`, meta description, canonical, OG, and Twitter tags via `react-helmet-async`.
- **Structured data (JSON-LD)**: Broad, correct coverage —
  - `WebSite` + `LegalService` (organization) in `client/index.html`
  - `Organization` at app root (`App.tsx`)
  - `FAQPage` on `/faq` (`FAQ.tsx`) **and** per-service FAQ blocks
  - `LegalService` + `BreadcrumbList` per service (`ServicePage.tsx`)
  - `ItemList` on `/services`, `Blog` on `/blog`, `BlogPosting`/`Article` per post
- **robots.txt** (repo version): Sophisticated. Blocks training-only crawlers (GPTBot, Google-Extended, CCBot, anthropic-ai, Bytespider, Applebot-Extended) while allowing search + AI-retrieval bots (Googlebot, Bingbot, OAI-SearchBot, PerplexityBot, ClaudeBot, social-preview bots). Correctly allow-lists the `/api/trpc/blog.*` endpoints so the JS renderer can fetch blog content.
- **sitemap.xml**: Server-generated (`server/sitemapRoute.ts`), includes all static pages, all 10 service slugs, and all published blog posts with `lastmod`/`changefreq`/`priority`. Cached 1h.
- **`llms.txt`**: Present, with brand positioning for AI answer engines.
- **Geo targeting**: `geo.region`/`geo.position`/`ICBM` for California + `areaServed: California` in structured data — appropriate for a CA-focused service.
- **Bing verification**: `msvalidate.01` meta + `BingSiteAuth.xml` (in repo).
- **Performance**: Vite code-splitting, lazy routes with retry, font `display=swap`, preconnect/dns-prefetch for fonts.

## 2. Critical Issues — Detailed

### P0-1 — Production is serving a stale build 🔴

Direct comparison of the **live** `https://talk-to-my-lawyer.com/` HTML against this repo's `client/index.html`:

| Element | Live (production) | Repo (this codebase) |
|---|---|---|
| JSON-LD structured data | **absent** (0 blocks) | present (2 blocks: WebSite + LegalService) |
| Bing `msvalidate.01` meta | **absent** | present |
| `og:title` | "Talk to My Lawyer — Professional Legal Letters" | "Attorney-Drafted Legal Letters — Demand & Cease and Desist \| Talk to My Lawyer" |
| `twitter:image` | relative `/logo-main.png` (invalid for scrapers) | absolute URL |
| viewport | `...maximum-scale=1` (blocks pinch-zoom) | no max-scale (accessible) |
| robots.txt sitemap target | `www.talkmylawyer.com` | `www.talk-to-my-lawyer.com` |

**Action:** Deploy current `main`/release. This single step ships richer structured data, fixes the OG/Twitter previews, restores Bing verification, removes the mobile-usability penalty, and corrects the sitemap reference — with zero new code.

### P0-2 — Duplicate domains, no 301 canonicalization 🔴

Observed live (2026-06-28):

| Host | Status | Notes |
|---|---|---|
| `talk-to-my-lawyer.com` | `200` | identical ETag `djjmmyy9vy806jf` |
| `www.talk-to-my-lawyer.com` | `200` | identical ETag — this is the `og:url` host |
| `www.talkmylawyer.com` | `200` | identical ETag — this is the host in the **live** sitemap/robots |
| `talkmylawyer.com` (apex) | `405` | misconfigured |

Three live, identical copies of the entire site with **no redirects between them**, and the canonical signals disagree (sitemap says `talkmylawyer.com`, `og:url` says `talk-to-my-lawyer.com`). This is the classic duplicate-content failure mode: crawl budget and link equity are diluted, and Google may consolidate to a domain you don't want.

**Action (infra, ~30 min):**
1. **Pick one canonical host.** Recommend `https://www.talk-to-my-lawyer.com` (it matches the repo's `og:url`, canonicals, and sitemap generator). Decide www vs apex and commit to it everywhere.
2. **301-redirect all other hosts** to the canonical host at the edge (Caddy — production runs `server: Caddy`). Example:
   ```caddy
   talk-to-my-lawyer.com, talkmylawyer.com, www.talkmylawyer.com {
       redir https://www.talk-to-my-lawyer.com{uri} permanent
   }
   www.talk-to-my-lawyer.com {
       # ... app reverse_proxy ...
   }
   ```
3. **Make every internal signal agree** on that host — canonicals, `og:url`, sitemap `<loc>`, and the `Sitemap:` line in robots.txt. (The repo is already consistent on `www.talk-to-my-lawyer.com`; just verify after the deploy.)
4. In Google Search Console, register all variants and confirm the canonical resolves.

### P0-3 — Client-side rendering / empty shell 🟠

Every route's initial HTML body is `<div id="root"></div>` with no content, and the static shell serves the same default `<title>` and description for `/`, `/services/demand-letter`, `/blog/*`, etc. The per-URL title/content/canonical/JSON-LD only exist after React + Helmet run.

- Googlebot renders JS, so this mostly works for Google — but rendering is deferred and budget-limited, slowing discovery of new blog/service pages.
- **Bing, LinkedIn/Twitter/Slack/Discord scrapers, and most AI answer engines do not execute JS** — they see the generic homepage title/description on *every* URL, and no body text. That undercuts social sharing previews and AI citations (which is a stated goal of the `llms.txt`).

**Action (architectural — recommend, scope before implementing):**
- Add **prerendering / SSG for the marketing + blog/service routes** (the public, content-heavy pages). Options, lowest-effort first:
  - `vite-plugin-prerender` / `vite-react-ssg` to emit static HTML for `/`, `/pricing`, `/faq`, `/terms`, `/privacy`, `/services`, `/services/:slug`, `/blog`, `/blog/:slug` at build time (service/blog slugs are already enumerable via `shared/serviceSlugs.ts` and the DB).
  - Or a prerender service (e.g. Prerender.io) behind Caddy, serving cached HTML to non-JS bots.
  - Full SSR is the heaviest option and likely unnecessary for what is mostly static content.
- This is the only change that raises the *ceiling* on non-Google visibility; do it after P0-1/P0-2.

## 3. Secondary Improvements (P1/P2)

- **P1 — Static shell has no `<link rel="canonical">`.** Intentional for an SPA (a hardcoded homepage canonical would mis-tag sub-pages for non-JS crawlers). This becomes a non-issue once prerendering (P0-3) emits per-page canonicals into the static HTML. Until then, ensure *every* public page component sets its own canonical (audit `ClientPortal`, `ContentCalendar`, `NewsletterTemplate` — these had only basic/absent canonicals).
- **P1 — `meta name="keywords"`** is present in the live HTML. It's ignored by Google and can signal low-quality optimization; harmless but worth removing on the next pass.
- **P2 — OG image is the logo on every page.** A 1200×630 branded share image (and per-service/per-post variants where they exist) will materially improve social CTR vs. a square logo.
- **P2 — Add `AggregateRating`/`Review` structured data** if you have genuine reviews — eligible for star rich results on a `LegalService`. Only with real, policy-compliant review data.
- **P2 — Internal linking & content depth.** With 10 service pages + a blog, ensure services cross-link to relevant blog posts and vice-versa (topic clusters) to spread authority. Confirm each service page has substantial unique body copy (not just schema).
- **P2 — Image optimization.** Hero/attorney/security PNGs are served unoptimized; convert to WebP/AVIF with width/height attributes to improve LCP/CLS (Core Web Vitals are a ranking factor).
- **P2 — Add Google Search Console + (optionally) GA4.** Bing is verified; GSC is the single most important free source of query/impression/click data and indexing diagnostics. There is currently no GSC verification or analytics in the page.
