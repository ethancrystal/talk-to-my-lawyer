# SEO Audit — talk-to-my-lawyer.com (2026-06-27)

> Scope: every public page on the live site plus the codebase that produces them.
> Method: live HTTP inspection (raw `curl` + Googlebot UA), repo source review of
> the SEO/serving layer, SERP visibility spot-checks. Semrush data was requested
> but the connected Semrush plan does not include MCP/API access, so visibility is
> assessed from SERP checks and on-page signals rather than Authority Score / traffic
> estimates.

## TL;DR — the single most important finding

**The codebase already implements strong, modern SEO. Production is not serving it.**
The live deployment at `talk-to-my-lawyer.com` is a **stale build that predates the
current SEO/serving layer.** As a result, in production today:

| Signal | Repo (HEAD) | Live (production) |
| --- | --- | --- |
| Per-route `<title>` / `<meta description>` for crawlers | ✅ injected server-side per route (`server/spaRoutes.ts` → `injectSeoIntoHtml`) | ❌ every route returns the **same** generic homepage head |
| JSON-LD structured data in served HTML | ✅ `WebSite` + `LegalService` in `index.html`, plus per-route `jsonLd[]` | ❌ **zero** JSON-LD in served HTML |
| `og:title` | ✅ "Attorney-Drafted Legal Letters — Demand & Cease and Desist…" | ❌ old "Talk to My Lawyer — Professional Legal Letters" |
| Stale `keywords` meta / `maximum-scale=1` viewport | ✅ removed | ❌ still present |
| `robots.txt` | ✅ committed at `client/public/robots.txt`, points to sitemap | ❌ **HTTP 404** |
| `sitemap.xml` | ✅ dynamic route `server/sitemapRoute.ts` (static + 45 services + blog posts) | ❌ **HTTP 404** |
| `llms.txt`, `BingSiteAuth.xml` | ✅ real files in `client/public/` | ❌ return the **SPA HTML shell** (8 475 bytes, `text/html`) — Bing verification is broken |
| Prerendered per-route HTML for JS-blind / AI crawlers | ✅ `dist/_prerender` cache served by `server/_core/vite.ts` | ❌ not active |
| 404 routes return real `404` status | ✅ `shouldReturnAsset404` + per-route `statusCode` | ❌ unknown paths return `200` SPA shell |

**Action required: redeploy `main` (or whichever branch carries the prerender/SEO
serving layer) to production, then re-verify the rows above.** Most of the "gaps"
below are already fixed in code and only need to ship. This is the highest-leverage
SEO action available and requires no new engineering.

## How we look on the SEO spectrum (visibility)

- **Brand/intent SERP checks** for "talk to my lawyer attorney drafted legal letters"
  and "attorney drafted demand letter online flat fee free first letter" returned
  **competitors only** — LetterDash, JusticeDirect, demandletters.com, JD Woods Law,
  terms.law, LegalZoom — and **not** `talk-to-my-lawyer.com`. Not surfacing for a
  near-branded query is a strong signal of **very low current organic visibility.**
- This is consistent with the production state above: with no live `sitemap.xml`,
  no live `robots.txt`, identical head on every URL, and no JSON-LD or prerendering,
  search engines have little per-page signal to index and AI answer engines
  (Perplexity, Claude-Web, OAI-SearchBot — which do **not** execute JS) see only a
  generic shell. The site is effectively **near-invisible** on the SEO spectrum right
  now, despite a codebase that is well-positioned to rank.
- **Competitive context:** the demand-letter / cease-and-desist niche is contested by
  established flat-fee players (LetterDash $199, JusticeDirect, demandletters.com $299,
  terms.law $575). Differentiators worth leaning into on-page: "first letter free,"
  attorney-reviewed via Karish Law Firm, California focus, flat fee.

> Caveat: SERP spot-checks are directional, not a ranking export. A Semrush/GSC pull
> (Authority Score, indexed-page count, ranked keywords, impressions) should be run
> once production is fixed to get hard numbers and track recovery.

## What's done well (SEO best practices already followed — in code)

The repo demonstrates above-average SEO maturity for a React SPA:

1. **Server-side per-route SEO injection** (`server/spaRoutes.ts`) — `RouteSeo` defines
   `title`, `description`, `canonical`, and `jsonLd[]` for every public route and all
   45 service slugs; `injectSeoIntoHtml` writes them into the HTML *before* JS runs, so
   JS-blind crawlers get full per-page metadata.
2. **Prerender cache** (`server/_core/vite.ts`, `prerenderCache.ts`) — Puppeteer-captured
   post-hydration HTML per route, normalized to a single authoritative SEO tag set.
3. **Dynamic `sitemap.xml`** (`server/sitemapRoute.ts`) — static pages + 45 service pages
   + published blog posts with real `lastmod`, sensible `priority`/`changefreq`.
4. **Well-structured `robots.txt`** — blocks AI *training* crawlers (GPTBot,
   Google-Extended, CCBot, Bytespider…), allows search + AI *retrieval* bots
   (Googlebot, Bingbot, PerplexityBot, ClaudeBot, OAI-SearchBot…), allowlists the blog
   tRPC endpoints so Googlebot's renderer can hydrate blog content, and points to the
   sitemap.
5. **Rich JSON-LD** — `WebSite`, `LegalService`/`Organization` (with Karish Law Firm
   provider), `LocalBusiness`, `WebApplication`, `Article` (with `reviewedBy` attorney),
   `FAQPage`, `BreadcrumbList`, `ItemList`, per-service `LegalService`.
6. **Canonical URLs** on every public route (via `RouteSeo.canonical`).
7. **`llms.txt`** + **Bing Webmaster verification** (`BingSiteAuth.xml`, `msvalidate.01`)
   + **`X-Robots-Tag`** header as defense-in-depth.
8. **Semantic HTML** — single `<h1>` per page, sensible heading hierarchy, `article`/
   `main`/`section`/`header` landmarks; logo images carry descriptive `alt`.
9. **Blog SEO** — unique meta, `Article` + `BreadcrumbList` + conditional `FAQPage`
   schema, author + published/updated dates + reading time, and a "Quick Answer"
   callout engineered for AI-answer-engine citation.

## Genuine gaps that remain even after a redeploy

These are not fixed by shipping the current build and are worth a follow-up:

1. **apex vs `www` canonicalization (infra).** Both `https://talk-to-my-lawyer.com/`
   and `https://www.talk-to-my-lawyer.com/` return `200` with **no redirect**, while all
   canonical tags / `og:url` point to `www`. Add a permanent **301 from apex → `www`**
   (or vice-versa) at the edge (Caddy) so signals don't split across two hostnames.
2. **FAQ page (`/faq`) is missing `FAQPage` JSON-LD.** The FAQ content exists but the
   dedicated FAQ page does not emit `FAQPage` structured data (service pages and some
   blog posts do). Adding it unlocks FAQ rich results for high-intent queries.
3. **Blog Markdown images have no `alt` mechanism.** The Markdown renderer in
   `BlogPost.tsx` does not surface `![alt](url)` alt text — embedded blog images ship
   without `alt`, hurting accessibility and image SEO.
4. **`og:image` dimensions incomplete.** Only the homepage sets `og:image:width/height`
   (1200×630). Add them site-wide for reliable social/preview rendering.
5. **Sitemap `lastmod` for service pages is pinned** to a static date constant; fine for
   crawl-budget stability, but real update timestamps would improve recrawl priority
   when service copy changes.
6. **OG image is the logo, not a purpose-built share card.** A 1200×630 branded card
   ("First letter free · Attorney-reviewed") would lift social CTR.
7. **Post-fix monitoring.** Wire Google Search Console + Bing Webmaster coverage
   reports and a Semrush position-tracking project once production serves the real
   build, so recovery is measurable.
